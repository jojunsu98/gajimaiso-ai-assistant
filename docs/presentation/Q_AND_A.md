## 1. 일반 AI 채팅과 무엇이 다른가요?

“이 서비스는 질문을 받을 때 저장된 창원 자료를 읽고, 요약을 자동으로 AI에 전달합니다. 사용자가 매번 표를 붙여 넣지 않아도 되는 점이 핵심입니다.”

덧붙이기: 일반 AI도 자료를 제공하면 분석할 수 있습니다. 차이는 AI 자체의 우열이 아니라, **내 자료를 읽고 요약·저장·복원하는 과정을 서비스로 연결했다는 점**입니다.

<a id="q2"></a>
## 2. AI가 숫자도 직접 계산하나요?

“기본 계산은 서버 코드가 합니다. AI에는 계산 결과를 주고 이를 설명하도록 했습니다.”

덧붙이기: [summary.py](../../backend/app/services/summary.py)에서 기간·개수·합계·평균·극값·최근 두12개월 평균을 계산합니다. 누락 월이 있으면 임의로 채우지 않고 비교 자료 부족을 표시합니다. 계산 결과가 맞아도 AI의 설명에 오류가 생길 수 있으므로 수치와 기간을 함께 확인합니다.

<a id="q3"></a>
## 3. 왜 자료 전체 대신 요약을 보내나요?

“핵심을 짧게 정리하면 AI에 보내는 내용의 양을 줄일 수 있습니다. 대신 요약에 빠진 세부 정보는 답하기 어렵습니다.”

덧붙이기: 요약에도 입력 토큰 비용은 발생합니다. 현재 기본 출력 한도는800토큰이고 자동 재호출은 하지 않습니다. 금액 전체를 보장하는 예산 상한을 구현한 것은 아닙니다. [비용·한계 설명](../../README.md)

<a id="q4"></a>
## 4. AI를 새로 학습시킨 건가요?

“아닙니다. 질문할 때 참고할 자료를 건네는 방식입니다. 자료 요약과 답변 기준을 시스템 프롬프트라는 항목에 넣습니다.”

덧붙이기: [ChatService](../../backend/app/services/chat.py)가 만든 내용을 [OpenAIService](../../backend/app/services/openai_client.py)가 system 역할의 메시지에 넣습니다. 이를 컨텍스트 주입이라고 부릅니다. 자료 저장소를 벡터 검색하는 별도 RAG 시스템이나 모델 재학습을 구현한 것은 아닙니다.

<a id="q5"></a>
## 5. 자료를 바꾸면 답변도 바뀌나요?

“새 질문에서는 그때 저장된 자료를 다시 읽습니다. 이전 질문을 불러올 때는 당시 저장된 답변을 보여줍니다.”

덧붙이기: 답변 생성 중 다른 요청이 자료를 수정하면 그 답변은 요약을 만들었던 시점의 자료에 근거합니다. 대화에 마지막 요약도 보관합니다. 시연 중에는 자료 변경과 질문을 동시에 하지 않는 편이 해석하기 쉽습니다. 모든 작업을 하나의 잠금으로 묶은 구조는 아닙니다.

<a id="q6"></a>
## 6. 저장 실패나 동시 수정은 어떻게 처리하나요?

“저장이 확인된 뒤에만 성공으로 안내합니다. 실패하거나 결과가 불확실하면 목록부터 확인하고, AI를 자동으로 다시 부르지 않습니다.”

덧붙이기: 저장 확인 실패는 `saved:false`와503, 기존 대화가 다른 요청으로 바뀌면409를 반환합니다. 409는 ‘지금 편집한 기록이 그사이 달라졌다’는 뜻입니다. 최신 기록을 읽고 다음 작업을 결정해야 합니다. 저장되지 않은 답변을 자동 복구하는 별도 큐는 없습니다. [실패 규격](../submission/PRE_EVALUATION_RESPONSE.md)

<a id="q7"></a>
## 7. 화면과 서버를 왜 나눴나요?

“사용자에게 보여주는 일과, 자료를 검사하고 처리하는 일을 나누기 위해서입니다. 고장 난 부분을 찾고 고치기에도 도움이 됩니다.”

덧붙이기: 백엔드 안에서도 라우터는 요청을 받고, 서비스는 실제 일을 하고, 스키마는 입력과 출력의 형식을 정합니다. 의존성 주입은 필요한 일을 하는 대상을 밖에서 연결해 주는 방식입니다. 검사할 때 실제 AI 대신 정해진 답을 내는 더미를 연결할 수 있지만, 더미 검사와 실제 GPT 성공은 따로 기록합니다.

<a id="q8"></a>
## 8. 입력값은 어떻게 검사하나요?

“날짜가 맞는지, 숫자가 정수인지, 글이 너무 길지 않은지 화면과 서버에서 확인합니다.”

덧붙이기: 서버의 Pydantic 검사는 `YYYY-MM-01` 월 대표일, 정수 값, 메모500자, 질문2,000자 등의 규칙을 확인합니다. 예를 들어 `date: "2026-13-01"`이나 `value: "숫자아님"`은 올바른 형식이 아닙니다. 검증 실패의 공통 응답은 아래와 같습니다. 이는 코드 계약을 설명하는 예시이며 이번에 서버에 보내서 실행한 결과가 아닙니다.

```json
{"detail":{"code":"validation_error","message":"입력의 필수 항목·형식·길이·역할·ID를 확인하세요. API 문서의 허용 범위를 따라야 합니다."}}
```

질문·답변·메모는 글자로 표시하는 `textContent`를 사용합니다. 사용자 글을 HTML 명령처럼 실행하지 않는 방식이며, 모든 특수문자를 지우는 방식은 아닙니다. [입력 검사](../../backend/app/schemas/data.py), [오류 응답](../../backend/app/main.py)

<a id="q9"></a>
## 9. 자료와 대화는 어떻게 저장하나요?

“Firestore 안에서 통계 자료와 대화 기록을 서로 다른 묶음에 저장합니다. 날짜별 자료를 찾는 일과 질문 기록을 다시 여는 일을 구분하기 위해서입니다.”

덧붙이기: `data`에는 date/value/memo를 월별 ID로 저장하고, `conversations`에는 서버가 정한 ID, 질문·답변 배열, 생성·수정시각, 마지막 요약·모델·사용량을 저장합니다. 같은 월은 덮어쓰는 대신 중복을 막습니다. 별도 검색용 인덱스를 새로 구성했다거나 백업·복제가 검증됐다고 주장하지 않습니다. 현재 전체 자료 조회 방식은 자료량이 커지면 개선할 필요가 있습니다.

<a id="q10"></a>
## 10. 키·접근 권한·CORS는 무엇이 다른가요?

“AI 비밀키는 서버가 AI 서비스에 연결할 때 쓰고, 접근 토큰은 사용자가 보호 기능을 열 때 씁니다. CORS는 어느 웹 주소에서 서버를 이용할지 정하는 별도 규칙입니다.”

덧붙이기: 비밀값은 코드 밖의 실행 설정인 환경변수로 관리합니다. Vercel에는 공개 API 주소만 설정하고 AI 키는 Render 서버에 둡니다. CORS 허용 주소를 바꾸면 Render 설정에 정확한 origin을 반영하고 배포 후 확인해야 합니다. CORS만으로 사용자를 인증할 수는 없습니다. 현재 앱은 여러 사용자의 권한을 따로 나누는 시스템이 아니라 단일 관리 접근값을 사용하는 구조입니다.

<a id="q11"></a>
## 11. 18/18은 무엇을 증명하나요?

“제공받은 네이토 사전평가에서 코드와 문서의18개 항목을 모두 통과했다는 뜻입니다. 실제 실행 확인과 최종 동료평가는 별도로 봅니다.”

덧붙이기: 실제 GPT 생성·저장·복원은2026-10-29 검증 기록이 있고, 2026-11-04에는 화면 캡처와 공개 접근, 문서 반영을 확인했습니다. 이번 발표자료 제작에서는 GPT를 다시 부르거나 자료를 수정하지 않았습니다. [평가 결과 요약](EVALUATION.md)

<a id="q12"></a>
## 12. 한계와 다음 개선은 무엇인가요?

“저장된 자료에 없는 원인이나 미래를 단정할 수 없고, 사용자별 권한 분리도 아직 없습니다. 자료가 많아졌을 때 더 효율적으로 요약하는 방식도 개선할 수 있습니다.”

덧붙이기: 캐시는 계산 결과를 잠시 보관해 재사용하는 방식입니다. 도입한다면 자료 추가·수정·삭제 때 캐시를 갱신해야 합니다. 증분 집계는 바뀐 부분을 중심으로 다시 계산하는 방식인데, 누락 월·극값·과거 값 수정과12개월 비교 구간까지 고려해야 합니다. 지금 구현돼 있다고 발표하지 않습니다.
